# `kb topic review <topic>` Command Contract

This document defines and documents the first deterministic command skeleton for the topic review workflow.

Version introduced: `v0.7.1`

## Command

```bash
kb topic review <topic>
```

Optional flags for the first skeleton:

```bash
kb topic review <topic> --dry-run
kb topic review <topic> --preview
kb topic review <topic> --json
kb topic review <topic> --force
```

`--preview` should behave like `--dry-run`.

## Purpose

The command turns generated topic-local importance candidates into a review queue. It does not perform scientific judgment.

The intended pipeline is:

```text
kb topic rank <topic>
        ↓
topics/<topic>/importance/
        ↓
kb topic review <topic>
        ↓
topics/<topic>/review/review_queue.md
topics/<topic>/review/review_summary.md
```

## Inputs

The command reads:

```text
topics/<topic>/importance/
```

Candidate files may be Markdown or JSON-like files, but the first skeleton does not need a full semantic parser. A conservative implementation may treat each candidate file as one reviewable item.

Recommended accepted input extensions:

```text
.md
.markdown
.json
.toml
.yaml
.yml
```

The command may also read topic metadata if existing:

```text
topics/<topic>/topic.md
topics/<topic>/status.md
topics/<topic>/relations/
topics/<topic>/graph/
```

These are optional and should not be required for the first skeleton.

## Outputs

Default output directory:

```text
topics/<topic>/review/
```

Required outputs:

```text
topics/<topic>/review/review_queue.md
topics/<topic>/review/review_summary.md
```

Future outputs may include:

```text
topics/<topic>/review/review_queue.json
topics/<topic>/review/items/
```

Do not add those until needed.

## Queue Format

`review_queue.md` should be Git-diff friendly.

Recommended structure:

```markdown
# Topic Review Queue: <topic>

Generated by: `kb topic review <topic>`

Candidate source directory:

```text
topics/<topic>/importance/
```

## Review Items

| review_id | candidate_id | source_item | proposed_decision | status | reviewer | evidence |
|---|---|---|---|---|---|---|
| tr-0001 | importance-0001 | topics/<topic>/importance/example.md | unknown | candidate | unassigned | see candidate file |

## Review Rules

- Treat all items as candidates.
- Do not accept a candidate without evidence.
- Preserve uncertainty.
- Store reviewed decisions under `topics/<topic>/reviewed/`.
```

## Summary Format

`review_summary.md` should include:

```markdown
# Topic Review Summary: <topic>

- Topic: `<topic>`
- Candidate directory: `topics/<topic>/importance/`
- Review directory: `topics/<topic>/review/`
- Candidate files found: N
- Review items generated: N
- Empty or unreadable candidates: N
- Generated queue: `topics/<topic>/review/review_queue.md`
- Generated summary: `topics/<topic>/review/review_summary.md`

## Next Step

Review one candidate at a time. Accepted / rejected / deferred decisions should be recorded under:

```text
topics/<topic>/reviewed/
```
```

## Review ID Generation

The first skeleton may generate stable IDs from sorted candidate files:

```text
tr-0001
tr-0002
tr-0003
```

Sort order should be deterministic:

1. path string ascending
2. file name ascending
3. extension ascending

Do not use random IDs.

## Candidate ID Extraction

The first skeleton may use a simple fallback strategy:

1. Try to find a line like `candidate_id: ...` in YAML/front-matter-like text.
2. Try to find a line like `id: ...`.
3. Otherwise derive from the file stem, e.g. `importance-example-paper`.
4. If still unavailable, use `candidate-0001` based on deterministic order.

The parser should be conservative. If extraction is uncertain, write `unknown` or the path-derived ID instead of guessing.

## Proposed Decision Extraction

The first skeleton may use a simple fallback strategy:

1. Try to find `proposed_decision: ...`.
2. Try to find `importance: ...`.
3. Try to find one of the conservative labels: `core`, `supporting`, `background`, `peripheral`, `unknown`.
4. Otherwise use `unknown`.

The command must not reinterpret content to assign a new label.

## Evidence Extraction

The first skeleton may use a simple fallback strategy:

1. Try to find lines beginning with `evidence:` or containing `processing/`, `wiki/`, `raw/`, `topics/`.
2. If nothing clear is found, use `see candidate file`.

Evidence extraction is only a convenience. It is not proof.

## Error Behavior

If the topic directory does not exist:

```text
Error: topic workspace not found: topics/<topic>/
Hint: run `kb topic init <topic>` first.
```

If the importance directory does not exist:

```text
Error: importance candidate directory not found: topics/<topic>/importance/
Hint: run `kb topic rank <topic>` first.
```

If no candidate files are found:

```text
No topic-local importance candidates found.
```

The command may still write a summary in non-dry-run mode if this helps review, but it must not create fake accepted decisions.

## `--dry-run` / `--preview`

Dry-run mode should print:

- candidate directory
- candidate file count
- planned output files
- whether existing files would be overwritten

It must not write files.

## `--json`

JSON output should describe the same deterministic facts:

```json
{
  "topic": "thermal-metamaterials",
  "candidate_dir": "topics/thermal-metamaterials/importance",
  "review_dir": "topics/thermal-metamaterials/review",
  "candidate_files": 3,
  "review_items": 3,
  "queue_path": "topics/thermal-metamaterials/review/review_queue.md",
  "summary_path": "topics/thermal-metamaterials/review/review_summary.md",
  "written": true,
  "warnings": []
}
```

## Overwrite Policy

Default behavior should be conservative.

If `review_queue.md` or `review_summary.md` already exists, the command does not overwrite silently. It should either:

- return an error with a hint to use `--force`, or
- write a timestamped file.

Current first behavior:

```text
Error: review_queue.md already exists. Use --force to overwrite.
```

## Safety Boundary

This command must not:

- call an LLM
- use embeddings
- perform semantic ranking
- accept candidates
- reject candidates
- defer candidates
- edit `raw/`
- edit `wiki/`
- write to `topics/<topic>/reviewed/`
- change `LLM/memory/`
- infer causal or method relations
- claim topic importance as a final judgment

## Acceptance Criteria

The command is acceptable for `v0.7.1` when:

1. `kb topic review <topic>` checks that the topic workspace exists.
2. It reads `topics/<topic>/importance/` deterministically.
3. It creates `topics/<topic>/review/` if needed.
4. It writes `review_queue.md` and `review_summary.md`.
5. It gives every review item a deterministic `review_id`.
6. It marks every generated item as `candidate`.
7. It does not automatically accept, reject, or defer any item.
8. It supports `--dry-run` or `--preview`.
9. It supports a simple `--json` report if the existing CLI style supports JSON.
10. Existing reviewed decisions are never overwritten.


## v0.7.2 queue usability update

`review_queue.md` is now treated as an editable review workbench rather than only a candidate list. The generated table should include:

```text
review_id
candidate_id
source_item
proposed_decision
final_decision
status
reviewer
confidence
evidence
uncertainty
review_notes
accepted_record_path
```

The source columns preserve candidate provenance. The decision columns give a human reviewer, Manager LLM, or Worker LLM a controlled place to record the actual review decision.

Use `kb audit-wiki` to check whether existing review queues have this usable format.
