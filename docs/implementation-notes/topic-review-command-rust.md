# Implementation Notes: `kb topic review <topic>` in Rust

This file is an implementation guide for `v0.7.1`. It is not a replacement for reading the existing codebase. Follow the existing `kb topic` command style, naming conventions, error handling, and JSON-report patterns already used by the project.

## Goal

Add a conservative command skeleton:

```bash
kb topic review <topic>
```

The command builds a Markdown review queue and review summary from existing topic-local importance candidate files.

It must not perform semantic review.

## Expected CLI Shape

If the project uses `clap`, the conceptual command shape is:

```rust
TopicCommand::Review {
    topic: String,
    dry_run: bool,
    preview: bool,
    json: bool,
    force: bool,
}
```

The `preview` flag should be treated as equivalent to `dry_run`.

## Suggested File Paths

For a normalized topic name `<topic>`:

```rust
let topic_dir = kb_path.join("topics").join(topic);
let importance_dir = topic_dir.join("importance");
let review_dir = topic_dir.join("review");
let queue_path = review_dir.join("review_queue.md");
let summary_path = review_dir.join("review_summary.md");
```

Do not write outside the topic workspace.

## Data Structure

A minimal internal struct is enough:

```rust
struct TopicReviewItem {
    review_id: String,
    candidate_id: String,
    source_item: String,
    proposed_decision: String,
    status: String,
    reviewer: String,
    evidence: String,
}
```

Default values:

```text
proposed_decision = "unknown"
status = "candidate"
reviewer = "unassigned"
evidence = "see candidate file"
```

## Candidate Discovery

Use deterministic ordering.

Pseudo-code:

```rust
let mut files = Vec::new();
for entry in fs::read_dir(&importance_dir)? {
    let entry = entry?;
    let path = entry.path();
    if path.is_file() && is_review_candidate_extension(&path) {
        files.push(path);
    }
}
files.sort_by(|a, b| a.to_string_lossy().cmp(&b.to_string_lossy()));
```

Accepted extensions:

```text
.md, .markdown, .json, .toml, .yaml, .yml
```

## Candidate Parsing

Keep this deliberately simple. Do not build a fragile parser that pretends to understand all candidate formats.

Recommended helpers:

```rust
fn extract_field(text: &str, keys: &[&str]) -> Option<String>;
fn extract_candidate_id(text: &str, path: &Path, index: usize) -> String;
fn extract_proposed_decision(text: &str) -> String;
fn extract_evidence(text: &str) -> String;
```

Field extraction can scan line by line:

```text
candidate_id: abc
id: abc
proposed_decision: core
importance: supporting
evidence: processing/text/example.txt
```

If a value is not found, fall back safely.

## Review ID Generation

Generate IDs based on sorted order:

```rust
format!("tr-{index:04}", index = i + 1)
```

This makes output stable across runs as long as candidate files are unchanged.

## Markdown Queue Rendering

Render `review_queue.md` as a simple table:

```markdown
# Topic Review Queue: thermal-metamaterials

Generated by: `kb topic review thermal-metamaterials`

Candidate source directory:

```text
topics/thermal-metamaterials/importance/
```

## Review Items

| review_id | candidate_id | source_item | proposed_decision | status | reviewer | evidence |
|---|---|---|---|---|---|---|
| tr-0001 | importance-0001 | topics/thermal-metamaterials/importance/example.md | unknown | candidate | unassigned | see candidate file |
```

Escape Markdown table pipes in cell values.

## Markdown Summary Rendering

Render `review_summary.md` with counts and warnings:

```markdown
# Topic Review Summary: thermal-metamaterials

- Topic: `thermal-metamaterials`
- Candidate directory: `topics/thermal-metamaterials/importance/`
- Review directory: `topics/thermal-metamaterials/review/`
- Candidate files found: 3
- Review items generated: 3
- Empty or unreadable candidates: 0
- Queue path: `topics/thermal-metamaterials/review/review_queue.md`
- Summary path: `topics/thermal-metamaterials/review/review_summary.md`

## Next Step

Review one candidate at a time. Do not accept any candidate without evidence.
```

## Dry Run

In dry-run mode:

- do not create directories
- do not write files
- print candidate count and planned output paths
- return success unless required input directories are missing

## Overwrite Policy

If output files exist and `--force` is not present, return an error:

```text
review_queue.md already exists. Use --force to overwrite.
```

Do not silently overwrite review work.

## JSON Output

If the project already has JSON patterns, match them. Minimal shape:

```json
{
  "topic": "thermal-metamaterials",
  "candidate_dir": "topics/thermal-metamaterials/importance",
  "review_dir": "topics/thermal-metamaterials/review",
  "candidate_files": 3,
  "review_items": 3,
  "queue_path": "topics/thermal-metamaterials/review/review_queue.md",
  "summary_path": "topics/thermal-metamaterials/review/review_summary.md",
  "written": true,
  "dry_run": false,
  "warnings": []
}
```

## Tests to Add

Add small focused tests consistent with the existing test style.

Suggested cases:

1. Missing topic directory returns a clear error.
2. Missing importance directory returns a clear error.
3. Empty importance directory generates zero review items or clear no-candidate output.
4. Two candidate files produce two deterministic rows.
5. Existing queue without `--force` is not overwritten.
6. `--dry-run` writes no files.
7. `--force` overwrites queue and summary.
8. Markdown table cells escape `|` characters.

## Forbidden Implementation Choices

Do not:

- add an LLM API call
- add embeddings
- call external network services
- read or write `raw/`
- write to `topics/<topic>/reviewed/`
- write to `LLM/memory/`
- automatically classify a paper as core/supporting/background from free text
- mix this command with `kb topic rank`
- make the command depend on a database
